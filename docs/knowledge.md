# 知识库使用与实现说明

知识库是平台原生能力，与 Skills、MCP 独立配置。不需要 MCP、Embedding 模型或独立向量服务；配置模型之前也可以创建知识库、上传文档和测试检索。

## 使用流程

1. 在顶部“配置 → 知识库”中，点击“新建知识库”，填写名称与说明。多个库通过顶部选择器切换。
2. 在“文档管理”点击“上传文档”，选择 UTF-8 TXT、Markdown 或可提取文本的 PDF，等待状态变为“可检索”。切到“检索测试”直接查询本地索引，不调用模型。
3. 配置模型后，在“配置 → Agent”选择目标助手，打开“知识库关联”并选择范围，确认检索内容可以发送给当前模型服务，再保存关联。
4. 回到对话，让助手查询资料。助手有 `knowledge_search`、`knowledge_read` 两个工具；回答下方会列出该轮实际检索或读取过的来源。点击可查看不可变版本的片段与分页解析原文。
5. 文档列表可搜索名称、筛选状态，点击名称查看详情与已发布原文。行末“•••”菜单提供“替换文件”“重新索引”“重试处理”与确认删除；知识库编辑/删除位于顶部“管理知识库”。处理失败可重试，也可上传修正后的版本。

未绑定知识库时不注册知识工具。关联变更只影响之后提交的任务，已提交任务使用保存的绑定快照；需要立即停止旧任务时应取消相应任务。文档与索引不在任务提交时复制：查询读取当时已发布的版本，删除的文档立即退出新检索。历史对话中已经产生的内容仍保留。

来源列表表示本轮真实检索/读取的资料，不表示模型的每一句话均已被自动核实。没有检索结果时工具返回空集合，工具说明要求模型说明缺少依据；不会构造不存在的来源。

## 解析与检索范围

| 项目 | 当前行为 |
| --- | --- |
| 文件类型 | UTF-8 TXT、Markdown、文本 PDF；Markdown 作为文本提取和展示 |
| 上限 | 20 MiB/文件、100 万提取字符、5000 个片段、PDF 1–1000 页 |
| 不支持 | OCR、扫描件、Office、加密或损坏 PDF、二进制/非 UTF-8 文本 |
| PDF 依赖 | Poppler 的 `pdfinfo`、`pdftotext`，检测后以参数数组执行，两个操作共享 15 秒期限并限制输出 |
| 中文 | `github.com/go-ego/gse@v1.1.0`、嵌入中文词典，离线分词；查询与索引使用同一规则 |
| 切分 | 按解析页、空白行段落，段内最长 600 个 Unicode 字符，优先句末/换行及词间空白，相邻窗口重叠 80 字符 |
| 检索 | SQLite FTS5；标题权重 3、正文权重 1；先匹配所有有效词，找不到再匹配任一词 |
| 分数 | 实际 SQLite BM25，越小越相关，通常为负值；不表示概率或语义相似度 |
| 查询 | 最多 500 字符、32 个去重后的有效词；管理 API 最多 10 个片段，Agent 每次最多 5 个、默认 3 个 |
| 原文 | 管理端每次最多 12000 字符；Agent 最多 4000、默认 2000；可用 `next_offset` 继续读取 |

检索测试只展示紧凑摘要：有效分词不超过 2 个时最多 140 字符，其余最多 220 字符（省略号另计），优先覆盖更多查询词；来源页保留完整片段与原文。Agent 检索仍保留最多 600 字符的摘要预算。已有索引立即使用紧凑摘要，新切片规则需对文档“重新索引”后生效，不改写历史来源。调整依据、操作与本地性能小样见 [knowledge-tuning.md](knowledge-tuning.md)。

这是小规模资料的关键词全文检索，不是语义检索。没有大规模语料评测；词汇差异较大时需要改用资料中的关键词。非常短的段落过多时应合并或拆分文档，避免索引碎片超过上限。

本地 PDF 支持需另行安装：macOS 使用 `brew install poppler`；Debian/Ubuntu 使用 `apt-get install poppler-utils`。Dockerfile 已添加 `poppler-utils`，但当前环境未安装 Docker，引擎中的实际构建和运行仍待验收。缺少依赖时会提示并将该 PDF 标为失败，安装后可重试；TXT、Markdown 和基础对话不受影响。

PDF 页码来自实际提取页与 `pdfinfo` 的页数核对。段落编号来自解析文本；字符范围位于去除首尾空白的段内，`start` 从 0 起、缺省为 0，`end` 不含末端字符。分页读取的 `offset` 则基于完整解析文本，单位也是 Unicode 字符。来源页展示解析文本，不渲染原 PDF 版式或文档 HTML。

## 架构与存储

Go 的 `internal/knowledge` 不依赖 Runtime 或 MCP。`Core` 管理生命周期、后台作业、绑定及访问范围，`Provider` 只要求 `Search` / `Read`，当前由 `LocalProvider` 实现。Go 平台执行面从运行快照取得授权，再调用 Core。Node 使用 Pi Durable 的原生工具注册 API，经私有 NDJSON 请求检索，不打开平台数据库、不实现检索引擎。

| 表 | 作用 |
| --- | --- |
| `knowledge_bases` | 名称、说明、创建时间和删除标记 |
| `knowledge_documents` | 知识库归属、稳定标题、已发布版本和删除/文件清理状态 |
| `knowledge_versions` | 原文件元数据、处理状态、错误、字符/片段数 |
| `knowledge_chunks` | 不可变版本片段、真实页/段/字符定位 |
| `knowledge_fts` | 仅当前已发布版本的分词索引 |
| `knowledge_bindings` | Agent 与知识库的显式关联，每个助手最多 16 个 |
| `run_sources` | 每轮实际来源的文档/版本/位置引用，不复制原文或分数 |

原文件在 `<data>/knowledge/<document_id>/<version>/original`，完整提取页在同目录 `text.json`，临时上传在 `<data>/knowledge/staging/`。文档标题保持首次上传时的稳定名称，每个版本另外保存实际上传文件名。平台 SQLite 归 Go 所有，Runtime Store 仍独立。

版本状态为 `queued → processing → ready / failed`。解析和分词在发布事务外完成；片段、FTS 与 `active_version` 在同一事务内切换。更新失败保留旧版本检索；失败重试复用该失败版本的原文件，已就绪文档重新索引则创建新版本。旧版本索引退出检索，但片段和解析原文保留供历史来源读取。

删除先在事务中标记、移除索引与片段，再清理文件。删除知识库还会解除关联。文件清理失败保留 `cleanup_pending`，界面提示可重试，后台继续清理；历史引用标识保留并返回删除状态。来源 ID 由真实文档、版本和片段位置生成，读取时再次校验归属。

服务启动将中断的本地索引作业重新排队，清理未提交的暂存及孤立版本目录。这类确定的本地索引工作可以重建；Agent 模型任务和 MCP 外部副作用仍遵循原有“不自动重放”规则。

当前数据库版本为 **8**（知识库表由版本 5 引入）。版本 1–7 自动迁移至当前版本；升级前停止整个服务并备份完整数据目录，回退需恢复完整旧备份。知识原文也必须包含在备份中。

## 管理 API 与执行面

所有管理 API 均要求管理员登录；写操作沿用 Cookie、CSRF 和来源检查。

| 方法与路径 | 作用 |
| --- | --- |
| `GET/POST /api/knowledge/bases` | 列表/创建 |
| `PUT/DELETE /api/knowledge/bases/{id}` | 修改/删除知识库 |
| `GET /api/knowledge/status` | PDF 依赖状态和限制 |
| `GET/POST /api/knowledge/bases/{id}/documents` | 文档列表/单文件 multipart 上传，字段 `file` |
| `PUT /api/knowledge/bases/{id}/documents/{document}` | 上传替换版本 |
| `DELETE /api/knowledge/documents/{document}` | 删除文档/重试文件清理 |
| `POST /api/knowledge/documents/{document}/retry` | 重试失败版本或重新索引 |
| `POST /api/knowledge/search` | 管理员本地检索，可指定 `knowledge_ids` |
| `GET /api/knowledge/sources/{source}?offset=0&limit=4000` | 读取来源片段及分页原文 |
| `GET/PUT /api/agents/{agent}/knowledge` | 查看/保存指定助手关联；非空关联要求 `confirm: true`，旧 `/api/agent/knowledge` 仍指默认助手 |

运行时仅注册有授权的知识工具。Go 不接受模型传入的新权限：查询范围必须是提交快照的子集，读取来源也检查文档归属，终态任务不再接受新请求。Runtime 的请求有 ID、8 秒等待期限及取消消息，Go 同时最多处理 32 个请求、单次最长 10 秒；成功回复前持久化真实来源。结果和正文作为业务数据返回，不写入普通运行诊断或后台日志。后台日志只记录文档标识及固定错误类别。

## MCP 扩展与验证

MVP 提供内部 Provider 边界，**未实现知识库专用的 MCP 双向适配**。当前已有通用 MCP 功能继续可用，但不会自动把任意 MCP Server 当作知识库。

接入具体 MCP 知识源时，新增 Provider 适配并显式映射其实际工具、参数、片段、真实分数与定位；缺少读取能力时明确返回不可用，不能填造内容。对外暴露原生检索时，用独立适配层调用相同 Core，并补齐服务级身份、范围授权和取消。两者都不要求修改 Agent 的统一知识工具协议，也不让 Core 依赖 MCP。

验证分为三层：

- Go：中英文检索、查询转义、知识库范围与跨库来源拒绝、更新失败保留旧索引、原子切换/重新索引、历史/删除引用、处理恢复、类型/字符/片段限制、真实 Poppler 文本 PDF 页码及空白扫描件拒绝、认证管理 API、提交范围快照和来源记录、schema 1–7 → 8。
- Runtime：实际 Pi Durable 工具注册、私有 Go RPC、未绑定不开放、取消请求和迟到回复；继续运行已有 Skills/MCP 与故障测试。
- 完整进程及 Chromium：本地协议模型触发实际 Go 检索，验证独立工作台、上传/状态/测试检索、关联确认、回答来源、解析原文安全显示、失败/成功更新、历史版本、删除、390px 布局、完整 Go/Node 重启后文档和引用保留。

运行 `make build`、`make test`、`python3 tests/e2e.py`；浏览器命令与截图目录见 README。模型使用本地协议服务，未以此宣称真实外部模型、第三方 MCP 产品或 Docker 已验收。
