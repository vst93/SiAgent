# SiAgent 知识效果专项计划（轻量优先）

> 状态：K0–K6 已实施并验证，见 `docs/progress.md`。  
> 目标：在保持轻量、单机、SQLite、低资源占用的前提下，把知识问答从“能用”做成“有效果、可度量、可迭代”。  
> 关联计划：`docs/plan-extensions-and-integration.md`（扩展体系、模型生态、高级工具、Integration API）。

## 0. 结论摘要

v1 不做 Embedding，不做向量索引，不引入独立向量数据库。

知识效果走一条轻量流水线：

```text
解析 → 结构化 → 切分
     → FTS5/BM25 索引
     → 查询扩展（规则 + 可选 LLM）
     → 多查询 BM25 融合
     → 启发式重排 / 可选 LLM 重排
     → 上下文组装
     → 证据优先回答 + 引用 + 拒答
     → 评测 + 反馈
```

核心判断：

1. **先建立评测与 trace，再谈优化。** 没有黄金问答集，所有调参都不可验证。
2. **先做结构化，再做“语义”。** 企业资料的主要损失发生在解析和切分阶段，不是向量阶段。
3. **关键词检索是主线，不是临时方案。** 制度、手册、条款、编号、专有名词场景，BM25 仍然很强。
4. **用查询扩展补语义。** 用现有聊天模型生成关键词/同义查询，比引入 embedding 基础设施更轻。
5. **重排先做启发式。** 标题、章节、短语覆盖、位置、文档权重已经能提升很多；LLM 重排只作为可选增强。
6. **答案必须有依据。** 引用、拒答、claim 校验比“让模型自由发挥”更重要。
7. **Embedding/向量是可选增强。** 只有在评测证明存在语义召回缺口时才引入，且不阻塞主线。

## 1. 现状

当前实现：

- `internal/knowledge/local.go`：SQLite FTS5 + gse 中文分词 + BM25；
- 先 AND 后 OR，标题权重 3、正文权重 1；
- 按页/段落切分，长段最多 600 字符、重叠 80 字符；
- `runtime/src/knowledge.ts`：模型通过 `knowledge_search` / `knowledge_read` 主动检索；
- 支持 TXT、Markdown、文本 PDF；
- 有不可变文档版本、来源定位、原子发布、删除隔离；
- 没有 embedding、没有 rerank、没有查询改写、没有评测台、没有反馈闭环。

当前的主要问题：

- Markdown 和 PDF 都没有结构解析，只有“页 + 空行段落”；
- 固定窗口切分会破坏条款、步骤、表格结构；
- 用户问法和资料写法不一致时，BM25 容易漏；
- 没有 rerank，Top-k 里经常混入弱相关片段；
- 模型是否检索、用什么词检索，完全依赖模型自行判断；
- 没有“资料中未找到”的稳定行为；
- 没有线上反馈和内容缺口运营。

## 2. 目标与非目标

### 2.1 目标

- 在选定场景上，检索命中率和答案可信度可量化提升；
- 支持中英文混合资料；
- 支持制度、手册、合同、表格、流程等企业常见结构；
- 回答能给出可打开、可核对的来源；
- 没有依据时能稳定拒答；
- 管理员能看懂“为什么检索到这个片段”；
- 每次调整切分/查询扩展/重排/prompt 都能跑回归；
- 保持单机、SQLite、低资源占用。

### 2.2 非目标

- v1 不做 embedding、向量检索、HNSW、sqlite-vec；
- 不追求“支持所有文档格式”；
- 不做通用网页爬虫或外部文档系统 Connector；
- 不做大规模分布式检索；
- 不承诺模型回答 100% 正确；
- 不做 OCR 全量支持、Office 全格式、图片理解；
- 不把知识效果完全交给某个第三方 MCP。

## 3. 度量与评测

### 3.1 指标

| 层 | 指标 | 说明 |
| --- | --- | --- |
| 检索 | Recall@k | 黄金证据是否出现在前 k 个片段 |
| 检索 | MRR@10 | 第一个正确片段的排名 |
| 检索 | nDCG@10 | 多证据排序质量 |
| 答案 | Answer correctness | 与黄金答案要点的一致性 |
| 答案 | Citation precision | 引用片段是否真的支持对应结论 |
| 答案 | Faithfulness | 回答中的 claim 是否有证据支持 |
| 答案 | Abstention accuracy | 该拒答时拒答，不该拒答时别乱拒 |
| 运营 | 空检索率 | 检索无结果的请求比例 |
| 运营 | 未命中问题数 | 用户问题没有足够证据 |
| 性能 | p50/p95 latency | 检索、查询扩展、重排、生成分别统计 |
| 成本 | token / 调用成本 | 查询扩展、LLM 重排、生成 |

初始目标（需用真实语料校准，不作为对外承诺）：

- Recall@5 ≥ 0.80；
- MRR@10 ≥ 0.65；
- Citation precision ≥ 0.90；
- Faithfulness ≥ 0.90；
- Abstention accuracy ≥ 0.85；
- 检索 p95（不含生成）< 300 ms；
- 查询扩展 + 检索 p95 < 1 s。

### 3.2 评测集

每个知识库维护自己的评测集：

```json
{
  "question": "出差住宿标准是多少？",
  "type": "fact | policy | procedure | table | comparison | multi_hop | unanswerable",
  "expected_answer": "……",
  "evidence": [
    {"document_id": "...", "version": 3, "location": {"page": 2, "paragraph": 5}}
  ],
  "tags": ["财务", "差旅"],
  "difficulty": "easy | medium | hard"
}
```

要求：

- 首批每个知识库 30–100 条；
- 覆盖事实、制度、流程、表格、对比、多跳、无答案；
- 由业务方提供问题，管理员整理；
- 评测集与调参集分开，保留 held-out；
- 支持 CSV/JSON 导入导出；
- 评测结果保存配置快照，便于对比。

### 3.3 评测方式

- 检索指标：基于 evidence 标注自动计算；
- 答案指标：
  - 规则/引用匹配优先；
  - LLM judge 辅助；
  - 人工抽检校准；
- 回归：
  - CI 跑小规模 smoke eval；
  - 大评测集手动运行；
  - 每次改切分、查询扩展、重排、prompt 都记录对比。

### 3.4 线上反馈

- 每条回答支持点赞/点踩；
- 点踩原因：答错、缺依据、来源不相关、资料过期、答非所问、太长/太短；
- 空检索、低分检索、用户重复提问进入“内容缺口”；
- 文档更新后，标记引用旧版本的答案可能过期；
- 反馈用于词表、查询扩展和重排规则优化。

## 4. 知识流水线

### 4.1 解析（Parser）

目标：保留结构，而不是只拿纯文本。

首批支持：

- TXT / Markdown：标题层级、列表、表格、代码块；
- PDF：页码、段落、标题、表格（尽力）、页眉页脚去除；
- DOCX：标题、段落、列表、表格；
- HTML：后续（仅本地文件，不做爬虫）。

DOCX 实现建议：

- 首选 `github.com/gomutex/godocx`（MIT、纯 Go、可读写 DOCX）；
- 如果标题级别/表格/列表暴露不足，直接用 `archive/zip` + `encoding/xml` 读取 OOXML：
  - `word/document.xml`；
  - `w:pStyle` 判断标题；
  - `w:tbl` 读取表格；
  - `w:numPr` 判断列表/编号；
- 不引入 LibreOffice/Pandoc 作为默认依赖；
- 只支持 `.docx`，不支持二进制 `.doc`。

解析输出：

```text
Block {
  type: heading | paragraph | list | table | procedure | code | footnote
  level?: number
  text
  page?
  bbox?
  section_path: string[]
  clause?: string
  table?: { headers, rows, caption }
  location: { page, paragraph, start, end }
}
```

原则：

- 标题层级保留；
- 条款编号保留；
- 步骤列表保持顺序；
- 表格整表保留，不拆成散字；
- 页眉页脚、页码、水印尽量去除；
- 解析失败明确标记，不静默产生空文档。

### 4.2 结构化（Structure）

- 构建文档树：标题 → 章节 → 子章节；
- 识别条款：`第X条`、`1.1`、`(a)` 等；
- 识别流程：步骤列表、编号步骤；
- 识别表格：表头、行、列、合并单元格（尽力）；
- 识别引用：`见第X条`、`参照附件`；
- 生成 section_path，例如 `["第三章 差旅", "3.2 住宿标准"]`。

### 4.3 切分（Chunking）

从“固定字符窗口”升级为“结构感知 + 父子片段”：

- 检索用 child chunk：较小、聚焦；
- 回答用 parent section：更完整上下文；
- 表格：整表 + 行组；
- 流程：步骤保持在一起；
- 条款：按条款切，不跨条款；
- 长段落：在句末/换行/空白处切；
- 目标大小：300–600 字符（中文），重叠 10–15%；
- 每个 chunk 带元数据：
  - document_id、version、section_path、page、clause、table_id；
  - block_type、position、parent_id；
  - char range；
  - content hash。

### 4.4 富化（可选）

v1 只做低成本富化：

- 关键词/同义词提取（规则 + 现有聊天模型可选）；
- 文档/章节标题补全；
- 条款号、编号、金额、日期等实体抽取；
- 表格表头补全。

后续可选：

- 为每个 chunk 生成问题视图（question views）；
- 生成 section/doc 摘要；
- 更复杂的知识编译。

原则：

- 富化失败不阻塞主索引；
- 涉及把资料片段发给模型时必须明确提示；
- 可配置开关。

### 4.5 索引

v1 只使用 FTS5：

- 标题、section_path、条款号、正文分别加权；
- 标题权重 3、正文 1，可根据评测调整；
- 中文继续使用 gse；英文归一化；
- 片段保留真实页/段/字符定位；
- 索引版本与文档版本解耦；
- 新索引构建完成后原子切换；
- 旧索引保留供历史来源读取。

v1 不建向量索引。

### 4.6 查询理解

- 语言检测与归一化；
- 查询分类：
  - 事实查询；
  - 制度/条款；
  - 流程/步骤；
  - 表格/数值；
  - 对比；
  - 多跳；
  - 寒暄/无关；
- 查询扩展：
  - 规则：同义词、领域词表、编号归一化；
  - 可选 LLM：生成 2–3 个检索友好的关键词查询；
  - 多查询结果去重；
- 过滤：知识库、文档标签、章节类型；
- 查询扩展可关闭，保证低延迟模式。

### 4.7 检索

v1 用多查询 BM25 融合：

- 原始查询 BM25；
- 扩展查询各自 BM25；
- RRF（Reciprocal Rank Fusion）融合；
- 去重：内容 hash、近重复；
- 多样性：可选 MMR，成本低；
- 标题/章节/条款命中加权；
- 精确短语/编号匹配加权；
- 父子扩展：命中 child 后带出 parent section；
- 相邻扩展：带出前后 chunk。

不做向量检索；不依赖 embedding。

### 4.8 重排

v1 先用启发式：

- 标题/section_path 命中；
- 查询词覆盖率；
- 精确短语；
- 条款/编号匹配；
- 位置与文档权重；
- 片段长度惩罚；
- 去重后的多样性。

可选增强：

- 用现有聊天模型对 Top 20 候选做一次 listwise rerank；
- 超时/失败回退启发式；
- 默认关闭或仅对“复杂查询”开启；
- 不引入 cross-encoder 服务。

### 4.9 上下文组装

- Token 预算；
- 证据优先：先放最相关、最完整的证据；
- 去重：重叠片段合并；
- 保留来源 ID、标题、页码、条款、section_path；
- 允许 parent section 补充上下文；
- 明确“证据不足”时的指令。

### 4.10 答案生成

- 证据优先 prompt：只根据提供的证据回答；
- 引用格式：
  - inline `[1]` / `[2]`；
  - 或结构化 citations；
  - 平台校验引用 ID 是否存在；
- 拒答：
  - 无检索结果；
  - Top 分数低于阈值；
  - 证据与问题明显不相关；
  - 输出“资料中未找到”，并给出可能相关的资料名；
- claim 级校验（可选）：
  - 把答案拆成 claim；
  - 检查是否有证据支持；
  - 不支持的 claim 标记/删除/提示管理员；
- 回答风格：简洁、均衡、完整，与现有 Agent 输出策略兼容。

## 5. 数据模型

v1 建议新增/修改：

| 表 | 作用 |
| --- | --- |
| `knowledge_bases.config` | 每库的 parser/chunker/retrieval/rerank 配置 |
| `knowledge_versions` | 解析器版本、切分版本、索引版本、config_hash |
| `knowledge_chunks` | 增加 parent_id、block_type、section_path、page、clause、table_id、content_hash |
| `retrieval_traces` | query、扩展查询、候选、分数、选择、耗时、配置快照 |
| `eval_sets` / `eval_questions` | 评测集与问题 |
| `eval_runs` / `eval_results` | 每次评测的配置、指标、逐题结果 |
| `answer_feedback` | run_id/message_id、rating、reason、comment |
| `content_gaps` | knowledge_id、query、count、last_seen、status |

v1 不新增向量表。

原则：

- 增量迁移；
- 不删除历史版本；
- 索引版本与文档版本解耦；
- 来源 ID 仍指向不可变文档版本；
- trace 只存必要信息，避免复制全文和密钥。

## 6. 扩展边界

| 阶段 | 归属 | 说明 |
| --- | --- | --- |
| Parser | 扩展 | 首方默认 + 第三方插件 |
| Structure | 核心 | 文档树/条款/表格识别 |
| Chunker | 核心，参数可扩展 | 先保证默认质量 |
| Embedder | 可选扩展 | v1 不做；后续由评测触发 |
| Reranker | 可选扩展 | v1 启发式 + 可选 LLM；不做 cross-encoder 服务 |
| Retriever / Index | 核心 | v1 FTS5 + 多查询融合 |
| Context assembly | 核心 | token 预算、父子扩展、去重 |
| Answer policy | 核心 | 引用、拒答、校验 |
| Eval / trace | 核心 | 不能交给插件 |

原则：

- 核心掌握编排、trace、引用和评测；
- 插件只替换阶段；
- 插件失败必须可降级；
- 不允许插件绕过权限和来源校验；
- 阶段契约由本计划确定，扩展计划据此实现 manifest/RPC。

## 7. 管理界面

知识库工作台建议增加：

- **文档管理**：现有功能 + 结构预览；
- **检索测试**：查询、模式、Top-k、trace；
- **评测**：评测集、运行、指标、失败案例、对比；
- **内容缺口**：未命中问题、聚类、状态；
- **设置**：parser、切分、检索模式、查询扩展、重排、拒答阈值。

检索 trace 展示：

1. 原始查询；
2. 规则/LLM 扩展查询；
3. 各查询的 BM25 候选与分数；
4. RRF 融合结果；
5. 启发式/LLM 重排前后；
6. 最终送入模型的片段；
7. 引用来源；
8. 各阶段耗时。

Agent 配置增加“知识行为”：

- 检索模式：自动/始终/关闭；
- Top-k；
- 是否启用查询扩展；
- 是否启用 LLM 重排；
- 引用展示；
- 拒答策略；
- 最大来源数。

## 8. 创新方向

### 8.1 知识编译（低成本版）

入库时生成多个视图：

- 原文视图；
- 结构视图（章节、条款、表格、步骤）；
- 关键词/同义词视图；
- 可选问题视图（后续）。

检索同时命中多个视图，再融合。先做规则和结构，不急着上模型生成。

### 8.2 结构化表格问答

- 表格识别与结构化；
- 按行/列/条件检索；
- 表头重复；
- 自然语言摘要；
- 支持“某条件下是多少”的查询。

### 8.3 答案验证与证据图

- 答案拆 claim；
- 每个 claim 绑定证据片段；
- 不支持的 claim 标记；
- 管理员看到“答案-证据”图；
- 资料冲突时提示。

### 8.4 内容缺口与冲突检测

- 高频未命中问题；
- 资料之间说法不一致；
- 文档更新后可能过期的答案；
- 自动聚类、状态管理、转内容任务。

### 8.5 查询类型路由

- 事实查询：BM25 + 短语；
- 条款查询：结构化 + 精确匹配；
- 流程查询：步骤检索 + 顺序保持；
- 表格查询：表格专用检索；
- 对比查询：多文档检索 + 表格；
- 汇总查询：多片段 + 摘要。

### 8.6 反馈驱动的优化

- 点踩 → 词表/重排规则；
- 未命中 → 内容缺口；
- 低分检索 → 同义词/领域词表；
- 评测集 → 回归门禁。

## 9. 里程碑

### K0：评测与 trace 基线

- 评测集格式与导入；
- 检索指标计算；
- trace 记录；
- 管理端“检索测试 + trace”；
- 用当前 FTS5 跑基线，记录指标；
- 不改变现有检索行为。

### K1：结构感知解析与切分

- 解析输出 block 结构；
- 文档树、section_path、条款、表格、步骤；
- 父子片段；
- 表格/流程专用切分；
- Markdown 结构解析；
- DOCX 支持（`gomutex/godocx` + OOXML 兜底）；
- 重建索引后跑评测对比。

### K2：轻量检索增强

- 查询扩展（规则 + 可选 LLM）；
- 同义词/领域词表；
- 标题/section_path/条款加权；
- 精确短语/编号匹配；
- 多查询 BM25 + RRF；
- 去重、可选 MMR、父子扩展；
- 每库检索配置；
- 失败回退原始查询。

### K3：重排与查询理解

- 查询分类；
- 启发式重排；
- 可选 LLM listwise rerank（Top 20）；
- 超时/失败回退；
- 延迟预算与评测对比。

### K4：证据优先回答

- 引用格式与校验；
- 拒答策略；
- claim 级校验（可选）；
- 回答风格；
- 评测：citation precision、faithfulness、abstention。

### K5：反馈与内容运营

- 点赞/点踩；
- 内容缺口；
- 冲突/过期检测；
- 词表/重排规则优化；
- 评测回归门禁。

### K6：创新能力

- 问题视图/知识编译；
- 结构化表格问答；
- 证据图；
- 查询类型路由；
- 领域词表学习。

### 可选附录：Embedding / 向量索引

不排期，由评测结果触发。

如果 K2/K3 之后，评测显示明显的语义召回缺口，再评估：

- OpenAI-compatible embedding 连接；
- SQLite BLOB + Go 暴力余弦；
- 可选 MMR / 混合融合；
- 10 万 chunk 以上再考虑 HNSW；
- 不使用 sqlite-vec（当前 `CGO_ENABLED=0` + modernc SQLite 不适合）；
- 默认关闭，不影响纯关键词部署。

## 10. 验收标准

### K0

- 能导入评测集并运行；
- 能看到每条查询的 trace；
- 记录当前基线指标；
- 不改变现有问答行为。

### K1

- 解析结果保留标题/条款/表格/步骤；
- chunk 带 section_path、page、clause、parent_id；
- Markdown 标题/列表/表格不再退化为纯文本；
- DOCX 标题/段落/表格可提取；
- 评测指标不下降，结构类问题提升；
- 重建索引失败可回滚。

### K2

- 多查询 BM25 + RRF 在评测集上 Recall@5 有可量化提升；
- 查询扩展失败回退原始查询；
- 检索延迟在预算内；
- 不引入新基础设施。

### K3

- 启发式重排提升 MRR/nDCG；
- 可选 LLM 重排可关闭、可回退；
- trace 能看到每阶段；
- 延迟/成本可控。

### K4

- 引用可打开、可核对；
- 无依据时稳定拒答；
- 评测集上 citation precision / faithfulness 达标；
- 不出现“编造来源”。

### K5

- 反馈可记录、可统计；
- 内容缺口可运营；
- 冲突/过期可提示；
- 评测回归可阻止明显退化。

### K6

- 在选定场景上验证创新点有效；
- 不以“功能存在”代替“效果提升”。

## 11. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 评测集偏差 | 优化方向错误 | 业务方参与、held-out、人工抽检 |
| 纯关键词语义泛化弱 | 口语化问题漏检 | 查询扩展、同义词、可选 LLM 改写 |
| 查询扩展增加延迟/成本 | 体验下降 | 默认规则优先，LLM 可选 |
| 解析质量差 | 后续全错 | 结构预览、失败标记、逐格式验收 |
| 表格/PDF 复杂 | 效果不稳定 | 先选 1–2 个场景打透 |
| LLM 重排成本 | 成本/隐私 | Top 20、可关闭、明确提示 |
| 过度依赖 LLM judge | 评测失真 | 规则+人工抽检+引用匹配 |
| 重建索引时间 | 运维成本 | 后台构建、原子切换、旧索引保留 |

## 12. 已定决策与待定项

已定：

1. v1 不做 embedding、不做向量索引；
2. 关键词检索 + 结构 + 查询扩展 + 启发式/可选 LLM 重排；
3. DOCX 进 K1，使用 `gomutex/godocx` 优先，OOXML 兜底；
4. 不支持 `.doc`，不做 OCR；
5. 评测与 trace 先于优化；
6. Embedding/向量作为可选附录，由评测触发。

待定：

1. 首批打透的场景：制度/手册、合同条款、表格数据、多文档对比，先选 1–2 个。
2. Markdown/PDF 结构解析的优先级。
3. 查询扩展默认是否启用 LLM，还是规则优先。
4. LLM 重排默认关闭还是仅复杂查询开启。
5. 拒答阈值：按分数、按证据覆盖，还是按模型自评。
6. claim 校验是否进入 v1，还是先做引用校验。
7. 评测集规模与维护责任人。
8. 引用格式：inline 编号、结构化 citations，还是两者都有。

## 13. 与扩展/API 计划的关系

- K0/K1 不依赖扩展体系，可以立即开始；
- K2/K3 不依赖 embedding/reranker 扩展，使用现有聊天模型即可；
- M3 先接 model + parser；embedder/reranker 降为可选；
- M4 的 `/v1/knowledge/search` 复用当前流水线，响应结构预留 trace/score/citation；
- K4/K5/K6 可以在 M4 之后继续迭代，不影响 API 稳定字段。
