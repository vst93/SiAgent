# 企业微信内部自建应用（兼容适配器）

新建智能机器人请优先阅读 [聊天渠道](channels.md)，使用 BotID/长连接 Secret。本文保留企业内部自建应用的独立协议与兼容 API；此模式仍需要公网加密回调。

目前已实现配置、回调协议、消息路由、持久化去重、异步 Agent 任务及出站队列，并通过本地协议服务与真实 Pi Durable Runtime 验证。**真实企业环境的 URL 保存、内部成员收发和公网网络条件仍未验收**，不得据本地测试宣布企业微信实际可用。

支持范围仅为企业内部自建应用的文本私聊，不包含微信客服、外部联系人、群聊、图片或语音。成员必须在应用可见范围内；非文本消息会收到文字范围说明，事件和带群会话标识的消息不进入 Agent。

## 配置步骤

1. 使用公开 HTTPS 部署 Go 入口，并设置 `SIAGENT_PUBLIC_URL` 为浏览器访问的源地址。反向代理同时转发 `/callbacks/wecom/`，不能给这个路径增加管理员登录或 CSRF 要求；回调自身使用签名与 AES 校验。
2. 在企业微信后台准备内部自建应用的 CorpID、应用 AgentID、Secret，以及接收消息配置的 Token、EncodingAESKey。按当前官方要求配置应用可见范围、服务器可信 IP 和域名。
3. 在 SiAgent“配置 → 渠道接入 → 新增渠道”选择“企业微信 · 自建应用（兼容）”，选择助手，先保持停用并保存。三个敏感值分别输入，之后留空保留原值，均不回显。应用 AgentID 是企微后台的数值，不是平台助手 ID。
4. 将界面给出的回调 URL、相同的 Token 和 EncodingAESKey 填入企微接收消息配置。平台处理 GET 验签解密，返回明文 echostr，并记录 URL 验证状态。
5. 在此启用渠道并确认成员消息、工具及检索片段会发送给绑定助手的模型服务。凭据测试只获取 access_token，不发送测试消息，也不证明回调或成员收发已通过。
6. 使用应用可见范围内的内部成员发送文本。检查实际收到的回复，并在“最近入站消息”“最近发送记录”核对消息、任务及投递状态。

一个企业应用只允许一份未归档渠道配置。归档后可重建独立渠道，不复用旧会话。企业和应用标识创建后固定；调整 Secret、Token 或 AES Key 时同步企微后台，先停用渠道再操作。修改助手绑定前也须先停用；新绑定使用独立的成员会话，不混用旧助手上下文。

停用渠道后暂停新入站和后续出站，已在途的发送不能撤销。已有 Agent 任务仍正常处理，可从对应会话取消。归档前先停用；归档解除助手绑定、取消尚未发送的回复，保留历史任务和消息。助手归档要求先解除所有未归档渠道绑定，包括停用的渠道。

## 会话、任务与回复

会话按企业应用、成员和所绑定助手映射。不同成员和应用不共享上下文；重新绑定另一助手时不继承旧助手上下文。成员发送 **`/new`** 可开启新会话，旧历史保留，旧任务不会自动取消。达到上下文上限时，失败通知会提示开启新会话。

管理后台可以查看渠道会话、取消任务和显式清理已结束历史，但不能从 Web 向该会话注入新消息；使用“新对话”可独立测试助手。即使执行 `/new`，旧渠道会话也保持只读属性。

回调只完成校验、去重和 SQLite 入站提交，随后确认接收，不等待模型。后台复用现有 FIFO 队列、并发限制、模型/能力快照、超时和取消，不另建 Agent 引擎。创建运行与入站记录的运行 ID 关联处于同一事务，避免崩溃后再次创建任务。

入站先保存接收时的助手绑定；后台创建 Agent 任务时冻结该助手的模型、指令及能力。队列满、助手停用、上下文超限等明确拒绝会形成通知，不自动重新执行任务。单渠道最多缓存 1000 条尚未创建任务的入站，满后不确认接收，交由企微按其回调重试规则处理。

等待超过 10 秒时，每条入站最多安排一次“排队或处理中”提示。最终结果已产生时，取消尚未发送的提示。提示及最终回复的实际发送时间受网络和发送队列影响。

文本以 UTF-8 字节分块，每块正文最多 1800 字节，另加分段编号，总长小于官方 2048 字节限制；最多 64 段，超长时明确告知剩余内容未发送。知识回答附加最多 8 条真实检索来源的标题、版本和页/段定位。原文管理页仍需管理员登录，不开放给成员公开下载。

## 投递与恢复规则

出站状态与 Agent 状态独立：

| 状态 | 含义及后续动作 |
| --- | --- |
| `pending` | 尚未尝试，等待渠道启用和前段成功 |
| `sending` | 发送尝试已持久化，正在请求企微 |
| `sent` | 企微返回成功接受，不代表成员已读或端到端送达 |
| `retry` | 尚未发出业务消息的凭据请求失败，或企微明确拒绝且错误码可重试 |
| `failed` | 明确拒绝、收件成员无效，或已达到重试上限 |
| `unknown` | 请求超时、无效响应或确认前进程退出，结果不明，不自动重发 |
| `blocked` | 同一回复前面的分段未确认成功，后续分段停止 |
| `cancelled` | 提示过时或渠道归档，停止发送 |

自动发送最多尝试 3 次，间隔 2 秒、5 秒。只将明确的 `-1`（系统繁忙）、`45009`（接口频率限制）、`40014` / `42001`（访问凭据失效）列入 API 错误重试；失效凭据先清缓存再获取。其他拒绝保留错误码和安全说明，不保存原始供应商错误正文。

“重试已拒绝的发送”只重新安排已明确失败的出站消息及被其阻塞的后续段，不重新执行 Agent。结果不明的出站不提供重试按钮，应先到企微人工核对。

平台依据持久化出站状态控制重发。请求关闭厂商按相同 JSON 内容过滤重复消息的选项，使不同入站产生的相同合法回复仍能发送；不会以这一选项承诺严格恰好一次。

服务重启后：

- 已发送不再发送；发送中的记录变为 `unknown`，停止其后续分段。
- 尚未尝试的出站可继续发送，但不会重新运行 Agent。
- 原有未完成或排队的 Agent 任务仍按平台规则标为中断，并生成说明通知。
- 仅入站落盘、尚未创建任务的消息变为未开始处理，通知成员重新发送，不静默自动创建旧任务。

回调以应用作用域和官方 MsgId 持久化去重。相同 MsgId、相同解析内容重复到达时确认接收；内容冲突时拒绝。已经接收的相同回调在渠道停用后仍能得到去重确认。

## 数据、鉴权和接口

schema **6** 增加 `wecom_channels`、`wecom_sessions`、`wecom_inbox`、`wecom_outbox`，并为会话保存永久 `channel_id`。渠道 Secret、Token、AES Key 以平台主密钥 AES-GCM 加密；启动检查包括渠道密文。访问凭据仅在进程内按配置缓存，更新 Secret 后不会复用旧缓存。

入站内容、模型回复及投递正文是业务数据，存放于平台 SQLite，不写入普通日志。管理诊断需登录，展示最近 50 条入站预览和 100 条出站元数据，消息预览作为文本渲染。出站普通状态只保留错误码与固定说明，不回显 Secret、access_token 或供应商原始响应。

公开回调限制请求体 256 KiB，验证 SHA-1 签名、AES-256-CBC、PKCS#7 padding、长度、接收 CorpID 和消息 AgentID；请求签名时间允许前后 5 分钟。回调数据库操作期限 3 秒，失败不确认成功。网络请求不占用平台调度锁，企微接口故障不使基础 Web 对话依赖企微可用性。

| 方法与路径 | 作用 |
| --- | --- |
| `GET/POST /api/wecom/channels` | 认证列表/创建 |
| `PUT/DELETE /api/wecom/channels/{id}` | 更新/校验后归档 |
| `POST /api/wecom/channels/{id}/test` | 只读凭据测试 |
| `GET /api/wecom/channels/{id}/diagnostics` | 认证业务预览及发送状态 |
| `POST /api/wecom/deliveries/{id}/retry` | 重试明确失败的发送 |
| `GET /callbacks/wecom/{id}` | 公开签名加密 URL 验证 |
| `POST /callbacks/wecom/{id}` | 公开签名加密消息接收 |

当前 schema 23，支持版本 1–22 → 23；渠道表在版本 6 引入，版本 7 增加持久化清理请求，版本 8 增加模型协议和参数，版本 9 将旧企微表迁移至通用 `channels` / `channel_*` 表，保留原 ID、密文与投递状态。升级前停止服务并备份完整数据目录，回退需恢复旧备份。

## 验证证据与官方依据

本地已覆盖：签名/密文/接收方错误、XML 多根拒绝、独立 Node 加密与 Go 解密互通、无管理员 Cookie 的 URL 验证、并发重复回调只创建一条入站和一个运行、成员隔离、`/new`、原有 FIFO、长文本分段、一次等待提示、限次重试、明确失败的单独重试、未知发送及分段停止、重启不重放、停用/归档/解绑约束、密钥脱敏和旧 schema 迁移。

`TestWecomCompleteLocalRuntimePath` 使用真实 Node/Pi Durable 子进程、本地模型协议服务及本地企微协议服务，验证从签名回调到实际模型执行和异步发送的完整链路。`make test` 会先构建并测试 Runtime，再执行包含此链路的 Go 竞态测试。单独运行 Go 测试时，未安装 Node 或未构建 Runtime 会明确跳过该项。

浏览器验证配置、密钥清空与不回显、回调地址、独立加密验证、URL 验证状态、桌面和 390px 布局。真实企业的待验收条件及证据清单见 [wecom-validation.md](wecom-validation.md)。
